================================================================================
                  NetScan - test plan / verification checklist
================================================================================

Purpose: a practical checklist to run through after building netscan_x64.exe
(or after any code change) to confirm every mode still works as expected.
All commands below use netscan_x64.exe - swap in netscan_x86.exe separately
if you need to verify the 32-bit build too, the flags are identical.

Run these on an actual Windows machine, on a network you're allowed to
scan. Replace 192.168.1.0/24 with your real subnet throughout. Where a
test needs "a host with a known open port", pick anything reachable on
your network (the router's web UI on 80/443 is usually a safe bet).

Each test lists: the command, what it's checking, and what a healthy
result looks like. Tests are grouped from cheapest/safest to most
demanding, so you can stop early if time is short and still have
confidence in the core scanning path.


================================================================================
1. SANITY CHECKS (no network range needed)
================================================================================

1.1  Help text renders correctly (encoding check)

     netscan_x64.exe --help

     Expect: readable Cyrillic text if your build has Russian strings,
     or clean English text - no garbled characters (mojibake) regardless
     of the current cmd.exe code page. Confirms WriteConsoleW output is
     working.

1.2  Missing required arguments are rejected cleanly

     netscan_x64.exe --ip 192.168.1.1

     Expect: usage text printed, exit without attempting a scan (no
     --ports given).

1.3  Malformed IP is rejected with a clear error, not a crash

     netscan_x64.exe --ip 999.999.999.999 --ports 80 --proto tcp

     Expect: "Некорректный IP адрес" (or equivalent) and a clean exit.

1.4  OUI database download

     netscan_x64.exe --update-oui

     Expect: downloads oui.txt next to the exe (~1.3 MB, ~52000 lines),
     prints byte count, exits without requiring --ip/--ports. Requires
     internet access; if it's not available, confirm the error message
     is informative rather than a silent hang.


================================================================================
2. BASIC PORT SCANNING (--mode full)
================================================================================

2.1  Single host, single known-open port

     netscan_x64.exe --ip 192.168.1.1 --ports 80 --proto tcp
                     --mode full --threads 5 --timeout 800

     Expect: "найдено:1", the port listed under TCP in both console and
     the output file.

2.2  Single host, a mix of open and closed ports

     netscan_x64.exe --ip 192.168.1.1 --ports 22,80,443,9,9999
                     --proto tcp --mode full --threads 10

     Expect: only genuinely open ports appear in the results; count
     matches what you'd expect from manually checking the device.

2.3  UDP with a protocol-aware probe (DNS)

     netscan_x64.exe --ip 192.168.1.1 --ports 53 --proto udp
                     --mode full --threads 5 --timeout 1500

     Expect: found, IF the target actually runs a DNS resolver
     reachable on UDP from your scanning host (most home routers
     qualify). This exercises the real DNS query payload, not an empty
     probe - if this fails but you know DNS is running, see HELP.txt
     section 3 for why (e.g. resolvers that only answer localhost, or a
     firewall specifically blocking port 53).

2.4  A full /24 sweep on a handful of ports, no --discover

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 80,443,445
                     --proto tcp --mode full --threads 100

     Expect: completes (will be noticeably slower than the --discover
     variant below - this is the expected baseline to compare against).
     Note the elapsed time printed at the end for comparison with 2.5.

2.5  Same sweep, with --discover

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 80,443,445
                     --proto tcp --mode full --threads 100 --discover

     Expect: dramatically faster than 2.4 on a typical home/office
     subnet where most of the 254 addresses are unused. Compare the
     "Хостов: N" alive count against what you know is actually plugged
     in.


================================================================================
3. FAST MODE
================================================================================

3.1  Fast mode against a single reachable host - correctness check

     netscan_x64.exe --ip 192.168.1.1 --ports 20-100 --proto tcp
                     --mode fast --threads 5 --batch 16

     Expect: identical set of open ports as running the same range in
     --mode full (cross-check the two). This validates the async
     connect+select logic isn't dropping or double-counting results.

3.2  Fast mode at scale - the real speed test

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254
                     --ports 21,22,23,25,53,80,110,143,443,445,3389,5900-5910
                     --proto all --mode fast --threads 50 --batch 32
                     --discover

     Expect: this is the flagship "everyday" command from HELP.txt
     example 2 - completes quickly, results consistent with a slower
     --mode full run of the same range (spot-check a few hosts).

3.3  --retries under simulated packet loss

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 80,443,445
                     --proto all --mode fast --threads 30 --batch 16
                     --retries 3 --timeout 1000

     Expect: no crash, no hang; if your network has any flaky links,
     compare the found-count against a --retries 1 run to confirm
     retries are actually recovering some otherwise-missed ports.


================================================================================
4. PARALLEL TCP+UDP AND --sequential
================================================================================

4.1  Default: TCP and UDP scanned at the same time

     netscan_x64.exe --ip 192.168.1.1 --ports 53,80,443,161
                     --proto all --mode full --threads 20

     Expect (in a real cmd.exe window, not redirected): two separate
     progress bars, one labeled TCP and one UDP, updating independently
     on their own fixed lines.

4.2  Forced sequential mode for comparison

     netscan_x64.exe --ip 192.168.1.1 --ports 53,80,443,161
                     --proto all --mode full --threads 20 --sequential

     Expect: single progress bar at a time (TCP first, then UDP), total
     elapsed time roughly the sum of both phases - noticeably longer
     than 4.1's total for the same target.


================================================================================
5. RESERVED ADDRESSES AND PORT DEDUPLICATION
================================================================================

5.1  x.x.x.0 / x.x.x.255 are skipped by default

     netscan_x64.exe --ip 192.168.1.0-192.168.1.255 --ports 80
                     --proto tcp --mode full --threads 20

     Expect: "Пропущено адресов вида x.x.x.0/x.x.x.255" line with a
     count of (at least) 2; neither .0 nor .255 shows up attributed to
     a real device in the "Device information" block if --info is added.

5.2  --include-reserved brings them back

     netscan_x64.exe --ip 192.168.1.0-192.168.1.255 --ports 80
                     --proto tcp --mode full --threads 20
                     --include-reserved

     Expect: no skip message; .0 and .255 are scanned like any other
     address (results will likely show nothing open there, which is
     also correct - the point is they were attempted).

5.3  Duplicate ports in the list don't create duplicate results

     netscan_x64.exe --ip 192.168.1.1 --ports 80,443,80,22,443
                     --proto tcp --mode full --threads 10

     Expect: "Портов: 3" in the summary (not 5) - confirms
     deduplication happened before scanning, not just at display time.


================================================================================
6. LIVE-HOST DISCOVERY (--discover) IN DEPTH
================================================================================

6.1  ICMP+ARP finds more than ICMP alone would

     If you have a device on your LAN with ICMP explicitly disabled in
     its own firewall (many managed switches/servers do this by
     policy), point --discover at a range including it:

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 80
                     --proto tcp --mode full --threads 50 --discover

     Expect: "Разведка (ICMP+ARP): живых N из 254 (в подсети M
     подключений)" - the ICMP-blocked device should still be counted as
     alive (found via ARP) as long as it's on your directly-attached
     subnet. If M (adapter count) is 0, this check can't run at all -
     verify you're not scanning from inside some unusual network
     namespace/VM setup.

6.2  A genuinely empty range shows the "nobody answered" warning

     netscan_x64.exe --ip 10.250.250.1-10.250.250.10 --ports 80
                     --proto tcp --mode full --threads 10 --discover

     Expect (assuming that range is actually empty on your network):
     "живых 0 из 10" plus the explanatory warning about possible causes.


================================================================================
7. DEVICE DIAGNOSTICS (--info)
================================================================================

7.1  Baseline device fingerprinting sweep

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254
                     --ports 53,80,443,161,445,5900-5910
                     --proto all --mode fast --threads 50 --batch 32
                     --discover --info --out result.txt

     For each device found, manually verify against what you know:
       - MAC vendor matches the actual hardware brand (needs oui.txt -
         see test 1.4 first)
       - TTL-based OS guess matches reality (Windows machines should
         show TTL<=128, most everything else TTL<=64)
       - "Тип (по портам)" guesses look sane for printers/cameras/etc.
         if you have any on the network

7.2  NetBIOS / mDNS / LLMNR on a real Windows machine

     Run 7.1 against a subnet containing at least one Windows PC with
     file sharing or a name-resolution service running. Expect at least
     one of NetBIOS/LLMNR to return a name matching the machine's actual
     hostname. If neither works but the machine is reachable, check on
     that machine: `ipconfig /all` (NetBIOS over Tcpip should say
     Enabled) and Windows Firewall's Network Discovery rules
     (NETDIS-LLMNR-In, NETDIS-NB_*-In) for the active network profile.

7.3  Self-scan (scanning the machine NetScan itself runs on)

     From the Windows machine at, say, 192.168.1.50, run:

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 445
                     --proto tcp --mode full --threads 30
                     --discover --info

     Find the line for 192.168.1.50 (the scanning machine's own IP) in
     the results. Expect NetBIOS/LLMNR to still resolve a name for it -
     this is the loopback-substitution behavior described in HELP.txt
     section 5 ("Self-scanning"). If it comes back empty while a
     neighboring machine's name resolves fine, that's worth reporting -
     it would mean the loopback workaround regressed.

7.4  SNMP sysDescr against real network gear

     If you have anything with SNMP enabled (most routers/switches/UPS
     units support it, sometimes off by default):

     netscan_x64.exe --ip 192.168.1.1 --ports 161 --proto udp
                     --mode full --threads 5 --info

     Expect: "SNMP sysDescr: ..." with a real, readable device
     description string.

7.5  --sort-os groups the device list by OS guess

     Re-run 7.1 with --sort-os added. Expect the "Device information"
     block reordered so all TTL<=64 devices are together, then all
     TTL<=128 (Windows) devices, rather than sorted by IP.


================================================================================
8. DEEPER HOSTNAME RESOLUTION (--deep-resolve)
================================================================================

8.1  SMB2/NTLMSSP handshake - the most reliable name source

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 445
                     --proto tcp --mode full --threads 30
                     --discover --deep-resolve

     Expect: any Windows machine with SMB enabled (i.e. found on port
     445) shows "SMB NetBIOS: имя=... домен=..." with its real computer
     name and workgroup/domain. If the network has an actual AD domain,
     also expect "SMB DNS: имя=... домен=..." with the real AD domain
     name - this is the detail worth double-checking on a domain
     network, since it was never validated against a real AD controller
     during development.

8.2  Reverse DNS via the gateway

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 445
                     --proto tcp --mode full --threads 30
                     --discover --deep-resolve

     (same command as 8.1 covers this too) - check for "PTR (обратный
     DNS): ..." lines. Whether these appear depends entirely on whether
     your router/DHCP server registers client hostnames - a "no PTR
     records at all" result can be completely normal on some routers.

8.3  Reverse DNS via an explicit DNS server (e.g. an AD controller)

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 445
                     --proto tcp --mode full --threads 30
                     --discover --deep-resolve --dns-server 192.168.1.5

     Use this on a domain network where the AD DNS server maintains a
     fuller reverse zone than the router. Compare PTR results against
     8.2's gateway-based lookup.


================================================================================
9. WMI HARDWARE/OS INVENTORY (--wmi)
================================================================================

Unlike every test above, --wmi requires real rights on the target
machine. Expect it to fail (with a specific, readable error, not a
crash or a hang) against anything you don't administer.

9.1  SSO against your own machine or a domain you're already on

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 135,445
                     --proto tcp --mode full --threads 30
                     --discover --wmi

     Expect: for machines where your current session has WMI rights -
     "WMI ОС:", "WMI загружена:", "WMI железо:", "WMI залогинен:" lines
     with real, correct data. Cross-check core count/RAM/OS version
     against Task Manager / System Properties on that machine directly.
     For everything else: a clean "WMI: не удалось (...)" line, never a
     silent gap or a crash.

9.2  Explicit credentials

     netscan_x64.exe --ip 192.168.1.50 --ports 135,445 --proto tcp
                     --mode full --threads 5 --wmi
                     --wmi-user someadmin --wmi-password ****
                     --wmi-domain CORP

     Expect: works the same as 9.1 but authenticates as the given
     account instead of your current session - useful for scanning as
     a service/admin account without changing who you're logged in as.

9.3  Speed check: --wmi against a range with mostly non-Windows devices

     netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 135
                     --proto tcp --mode full --threads 50
                     --discover --wmi

     Expect: this should NOT take minutes even though most devices
     won't have DCOM open - confirms the port-135 pre-check (HELP.txt
     section 7) is actually short-circuiting the slow ConnectServer
     path for non-Windows/firewalled hosts. If this run is much slower
     than 9.1, that's a regression worth reporting.

9.4  --wmi-gpu

     netscan_x64.exe --ip 192.168.1.50 --ports 135,445 --proto tcp
                     --mode full --threads 5 --wmi --wmi-gpu

     Expect: an additional "WMI видеоадаптер: ..." line with the real
     GPU model, on top of everything from 9.1.


================================================================================
10. IDLE TIME / LOGON TIME VIA TERMINAL SERVICES (--wts)
================================================================================

Same rights requirement as section 9 - expect a clean, specific error
against anything you don't administer, never a crash or hang.

10.1  SSO against a machine you're already logged into / a domain
      you're already on

      netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 135
                      --proto tcp --mode full --threads 30
                      --discover --wts

      Expect: "WTS сессия: DOMAIN\user", "WTS время логона: ...", and
      "WTS бездействие: N.N мин." for machines with an active
      interactive session your current session can query. Cross-check
      the idle minutes against reality (step away from the target
      machine for a known amount of time, then re-run and compare).
      For everything else: a clean "WTS: не удалось (...)" line.

10.2  Explicit credentials (reuses --wmi-user/--wmi-password/--wmi-domain)

      netscan_x64.exe --ip 192.168.1.50 --ports 135 --proto tcp
                      --mode full --threads 5 --wts
                      --wmi-user someadmin --wmi-password ****
                      --wmi-domain CORP

      Expect: works the same as 10.1 but authenticates as the given
      account. This is the one path in the whole tool that was hardest
      to validate without a real domain controller - LogonUserW with
      LOGON32_LOGON_NEW_CREDENTIALS behaves differently across Windows
      versions and domain-trust configurations in ways a sandboxed test
      environment can't reproduce. If this specifically misbehaves
      (works for 10.1 but not 10.2), that's the most likely place for a
      real bug to surface.

10.3  --wts and --wmi together in one run

      netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 135,445
                      --proto tcp --mode full --threads 30
                      --discover --wts --wmi

      Expect: both sets of fields appear for the same host (WMI's
      hardware/OS block plus WTS's session block) - confirms the two
      independent code paths don't interfere with each other when
      combined, and that credentials are shared correctly between them.

10.4  Speed check, same reasoning as WMI's 9.3

      netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 135
                      --proto tcp --mode full --threads 50
                      --discover --wts

      Expect: fast rejection for non-Windows/firewalled hosts, same as
      9.3 - confirms --wts's own port-135 pre-check is working, not
      just --wmi's.


================================================================================
11. REMOTE EXECUTION VIA TASK SCHEDULER (--remote-exec / --enable-discovery)
================================================================================

Same rights requirement as sections 9-10, same credential flags. This
is the one section that writes/executes on the target rather than only
reading from it - be a bit more deliberate about which range you point
it at.

11.1  A harmless read-only command as a first smoke test

      netscan_x64.exe --ip 192.168.1.50 --ports 135 --proto tcp
                      --mode full --threads 5
                      --remote-exec "whoami > C:\Windows\Temp\netscan_test.txt"
                      --remote-exec-timeout 10000

      Expect: "Remote-exec: выполнено, код возврата 0". Confirm on the
      target machine afterward that C:\Windows\Temp\netscan_test.txt
      was actually created and contains the SYSTEM account name (since
      the task runs as SYSTEM, not as whichever account you authenticated
      with). This test intentionally does its own redirection rather than
      using --remote-exec-output (section 11.6+ below) - useful as a
      baseline to confirm the task itself ran correctly, independent of
      whether output capture is working.

11.2  Explicit credentials

      netscan_x64.exe --ip 192.168.1.50 --ports 135 --proto tcp
                      --mode full --threads 5
                      --remote-exec "whoami /all > C:\Windows\Temp\netscan_test2.txt"
                      --wmi-user someadmin --wmi-password ****
                      --wmi-domain CORP

      Expect: same as 11.1, authenticating as the given account instead
      of the current session.

11.3  --enable-discovery against a machine with NetBIOS/LLMNR currently
      not answering

      First, confirm the "before" state with a normal --info scan
      against the target (see section 7). Then:

      netscan_x64.exe --ip 192.168.1.50 --ports 135 --proto tcp
                      --mode full --threads 5 --enable-discovery

      Expect: "Remote-exec: выполнено, код возврата 0" (PowerShell
      returning 0 doesn't guarantee every sub-command inside succeeded
      individually, since service-related ones are wrapped in
      -ErrorAction SilentlyContinue - check the target's actual firewall
      rule state directly with `Get-NetFirewallRule | Where-Object
      {$_.Name -like "NETDIS*"} | Select DisplayName,Enabled` if you want
      to confirm precisely). Then re-run the --info scan from before -
      NetBIOS/LLMNR should now answer where they didn't.

11.4  Timeout handling for a slow or hanging remote command

      netscan_x64.exe --ip 192.168.1.50 --ports 135 --proto tcp
                      --mode full --threads 5
                      --remote-exec "timeout /t 30" --remote-exec-timeout 3000

      Expect: the tool gives up politely after ~3 seconds ("не удалось
      получить результат задачи") rather than blocking for the full 30
      seconds the remote command would actually take - confirms the
      polling loop respects --remote-exec-timeout. The task itself may
      still be left running on the target until it finishes on its own
      in this specific case (the tool doesn't attempt to force-kill an
      already-started task it gave up waiting on) - worth being aware of
      if you set a --remote-exec-timeout much shorter than the command
      you're actually asking it to run.

11.5  Combine with --wmi and --wts in one pass

      netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 135,445
                      --proto tcp --discover --wmi --wts --enable-discovery
                      --mode full --threads 20

      Expect: all three independent blocks (WMI hardware/OS, WTS
      session, Remote-exec result) appear for the same host without
      interfering with each other - confirms the shared COM
      initialization across all three code paths is correct.

11.6  --remote-exec-output: basic capture (push channel should work
      on a normal LAN with no unusual firewall/policy restrictions)

      netscan_x64.exe --ip 192.168.1.50 --ports 135 --proto tcp
                      --mode full --threads 5
                      --remote-exec "whoami & echo second line"
                      --remote-exec-output

      Expect: "Remote-exec: выполнено, код возврата 0" followed by a
      "Remote-exec output:" block with two indented lines (the SYSTEM
      account name, then "second line"). Afterward, confirm there is
      NO leftover C:\Windows\Temp\ns_*.out file on the target - the
      push step's own Remove-Item should have cleaned it up on success.
      A leftover file after a *successful* capture would mean the push
      script ran but didn't get to (or skipped) its cleanup step - worth
      reporting as a bug.

      Also worth checking on the scanning machine itself: does Windows
      Firewall show an "allow this app" prompt the first time
      netscan_x64.exe opens its push listener? If so, on a managed/
      corporate scanning machine, --remote-exec-output may need
      netscan_x64.exe pre-approved for inbound connections (or the
      prompt answered) before it can work unattended.

11.7  --remote-exec-output: forcing the ADMIN$ fallback

      Temporarily block the push channel - e.g. a local outbound
      firewall rule on the target blocking powershell.exe, or blocking
      the scanner's IP/high ports outbound - then repeat 11.6.

      Expect: the same successful result and output content as 11.6,
      but via the ADMIN$ share fallback this time. From the outside
      this looks identical to 11.6 (the tool doesn't currently say
      which of the two channels actually delivered the data) - to be
      sure the fallback path specifically is what's being exercised,
      confirm via a packet capture or connection log on the scanner
      that no successful inbound connection was made to the push
      listener's port during this run.

11.8  --remote-exec-output: both channels blocked

      On top of 11.7's block, also cut off SMB/ADMIN$ access - e.g.
      temporarily disable File and Printer Sharing, or block port 445,
      or restrict admin-share access via local policy - then repeat.

      Expect: "Remote-exec: выполнено, код возврата 0" (the command
      itself still ran and exited fine) followed by "Remote-exec
      output: не удалось прочитать (...)", with the error text naming
      the leftover path (C:\Windows\Temp\ns_<uuid>.out). Confirm that
      file actually exists at that path on the target with the
      expected content, then clean it up by hand - the tool never
      managed to read it, so it never got the chance to delete it
      either.

11.9  --remote-exec-output-size: truncation

      netscan_x64.exe --ip 192.168.1.50 --ports 135 --proto tcp
                      --mode full --threads 5
                      --remote-exec "dir C:\Windows\System32 /s"
                      --remote-exec-output --remote-exec-output-size 256

      Expect: the output block contains only ~256 bytes worth of
      content (cut off mid-line is fine/expected), followed by a
      "Remote-exec output: усечено до 256 байт (см.
      --remote-exec-output-size)" note. Confirms the truncation
      detection (the "one extra byte" read past the buffer) works via
      whichever channel actually delivered the data.

11.10 --remote-exec-output: empty output + non-zero exit code together

      netscan_x64.exe --ip 192.168.1.50 --ports 135 --proto tcp
                      --mode full --threads 5
                      --remote-exec "exit /b 3" --remote-exec-output

      Expect: "Remote-exec: выполнено, код возврата 3" followed by
      "Remote-exec output: (пусто)" - confirms a non-zero exit code
      doesn't suppress or interfere with output capture, and that
      genuinely empty output is shown as an explicit "(пусто)" marker
      rather than a blank/missing block that could be mistaken for a
      read failure.


================================================================================
12. WS-DISCOVERY (--wsd)
================================================================================

Unlike --wmi/--wts/--remote-exec, this needs no credentials and no
rights - same "just works or cleanly doesn't" expectation as NetBIOS/
mDNS/LLMNR in section 7.

12.1  Baseline sweep against a mixed network

      netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 3702
                      --proto udp --mode full --threads 30
                      --discover --wsd

      Expect: "WSD Types: ..." for actual Windows machines, network
      printers/scanners, and NAS devices that answer WS-Discovery
      probes (most non-Windows/non-WSD-aware devices simply won't
      respond - that's normal, not a bug). Where XAddrs was present in
      the ProbeMatch, also expect "WSD name: ..." with a readable
      friendly name (e.g. the machine's display name in Explorer's
      Network view) - cross-check by opening \\<ip>\ or the "Network"
      folder on a Windows machine on the same subnet and comparing
      names.

12.2  Types without a name

      Some devices answer the Probe (so Types is populated) but either
      have no XAddrs in the ProbeMatch or the WS-Transfer Get to
      XAddrs fails/times out. Expect "WSD Types: ..." alone in that
      case, with no "WSD name:" line - not an empty/garbled name line.
      Printers and simpler embedded devices are the most likely
      candidates for this; a real Windows PC should normally give both.

12.3  Combine with --info's other name sources on the same host

      netscan_x64.exe --ip 192.168.1.50 --ports 3702,5353,5355,137
                      --proto udp --mode full --threads 5
                      --wsd --info

      Expect NetBIOS/mDNS/LLMNR/WSD name fields to appear together for
      the same host and agree with each other (all resolving to the
      same machine name, possibly in different cases/formats) -
      confirms --wsd doesn't interfere with the other resolution paths
      when run alongside them.


================================================================================
13. OUTPUT HANDLING
================================================================================

13.1  --resume + --when as a monitoring log

      netscan_x64.exe --ip 192.168.1.1-192.168.1.10 --ports 80,443
                      --proto tcp --mode full --threads 10
                      --out monitor.txt --resume --when

      Run this command TWICE in a row. Expect: monitor.txt ends up with
      two timestamped blocks separated by two blank lines, not
      overwritten. Timestamps should be a few seconds apart and match
      wall-clock time.

13.2  --sort-by-port produces a second file without touching the first

      netscan_x64.exe --ip 192.168.1.1-192.168.1.254
                      --ports 22,80,443,3389 --proto tcp
                      --mode fast --threads 50 --discover
                      --out byip.txt --sort-by-port

      Expect: both byip.txt (sorted by IP) and byip_by_port.txt (sorted

================================================================================
NOTES FOR WHOEVER RUNS THIS
================================================================================

- Tests in sections 7-12 (--info / --deep-resolve / --wmi / --wts /
  --remote-exec / --enable-discovery / --wsd) were built and unit-tested
  against simulated protocol responses during development (hand-crafted
  NetBIOS/SNMP/mDNS/LLMNR/SMB2/WS-Discovery servers), but could NOT be validated
  end-to-end against a real Windows domain, a live DCOM/WMI provider, a
  real Terminal Services host, or a real Task Scheduler - there was no
  such environment available at build time. Sections 9, 10, and 11 in
  particular (--wmi, --wts, --remote-exec/--enable-discovery) are the
  least-tested paths in the whole tool - all three were only confirmed
  to fail cleanly (no crash, no hang, a specific readable error) against
  closed ports and fake listeners under Wine, and separately confirmed
  not to interfere with each other when combined (test 11.5) - but
  never confirmed to actually succeed against a real target.
  Test 10.2 (--wts with explicit credentials) and section 11 as a whole
  are the hardest paths to have validated in a sandbox - LogonUserW's
  behavior with LOGON32_LOGON_NEW_CREDENTIALS, and a Task Scheduler
  task's actual execution/output behavior once registered, both
  genuinely depend on the target's real configuration in ways that
  can't be simulated. --enable-discovery specifically (test 11.3) has
  never been confirmed to actually flip the firewall rules it's
  supposed to on a real machine - only that the PowerShell one-liner it
  runs matches what was manually verified to work during an earlier,
  separate debugging session (see the git history around that point).
  If anything in sections 7-12 misbehaves against real infrastructure,
  that's expected to be where bugs surface first - please report
  specifics (command used, expected vs actual output) rather than just
  "it didn't work".
- The stricter mDNS parser (PTR/SRV records with DNS-compression
  support, section 7) and --wsd (section 12) are both new and were only
  exercised against a wine-hosted simulated server, never a real mDNS
  responder or WS-Discovery device - worth extra scrutiny on the first
  real run.
- --remote-exec-output (tests 11.6-11.10) is the newest and least-tested
  piece of the tool. Its TCP push/accept logic (the listener, the
  source-IP filter, the timeout path) was unit-tested standalone under
  wine with a fake local "target" thread and passed all three cases
  (successful receive, timeout with nobody connecting, wrong-source-IP
  rejection) - but the actual PowerShell one-liner that a REAL target
  runs to read its own output file and push it back has never executed
  on a real Windows machine, and neither has the ADMIN$ fallback read.
  Give tests 11.6-11.10 particularly careful attention, in order: 11.6
  confirms the push channel works AND cleans up after itself, 11.7
  confirms the fallback kicks in correctly when push is blocked, 11.8
  confirms a clean, honest failure (with the right leftover-file path
  in the error) when both are blocked.
- Always compare a new build's results against a known-good previous
  run when in doubt - most of these tests are about catching
  regressions, not proving correctness from a blank slate.
