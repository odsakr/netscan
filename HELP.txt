================================================================================
                    NetScan - консольный сканер локальной сети
                              для Windows Vista - 11
================================================================================


ЧТО ЭТО
================================================================================

NetScan - лёгкий консольный TCP/UDP сканер локальной сети для Windows,
написанный на C и скомпилированный кросс-компилятором mingw-w64 (собирается
из Linux, статическая линковка - никаких дополнительных DLL на целевой
машине не требуется). Работает на x86 (32-бит) и x64 (64-бит), от Windows
Vista до Windows 11 включительно.

Придуман как замена nmap для повседневных задач системного администратора,
когда нужен быстрый, лёгкий инструмент с наглядным прогресс-баром, который
не только находит открытые порты, но и по возможности сразу же отвечает
на вопрос "а что это вообще за устройство и как его зовут" - без установки
Npcap/WinPcap и без прав администратора.

Ключевые принципы:
  - Никаких сторонних драйверов (Npcap/WinPcap) - работает "из коробки".
  - Не требует прав администратора для базового сканирования.
  - Честный прогресс-бар и статистика в реальном времени.
  - Реальный асинхронный "fast"-режим (сотни/тысячи проверок одновременно
    на поток), а не имитация через много ОС-потоков.
  - Стоимость доп. диагностики (MAC/имя устройства/ОС) считается на ХОСТ,
    а не на ПОРТ - не замедляет сам скан портов.


СИНТАКСИС
================================================================================

netscan_x64.exe --ip <диапазон> --ports <список> --proto all|tcp|udp
                 --threads <N> --mode full|fast [доп. параметры]

Обязательные параметры: --ip, --ports
Всё остальное имеет разумные значения по умолчанию.


ПРИМЕРЫ ЗАПУСКА
================================================================================

1) Простейший скан одного хоста по паре портов (полный, надёжный режим):

   netscan_x64.exe --ip 192.168.1.1 --ports 22,80,443 --proto tcp
                   --threads 20 --mode full

   Медленно, но максимально надёжно - один запрос на порт за раз на поток.


2) Быстрый скан всей домашней подсети по популярным портам:

   netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 21,22,23,25,53,
                   80,110,143,443,445,3389,5900-5910 --proto all
                   --mode fast --threads 50 --batch 32 --discover

   --discover резко ускоряет скан больших диапазонов: сначала быстрый
   ICMP+ARP пинг находит РЕАЛЬНО живые хосты, и только по ним потом
   гоняются порты - вместо того чтобы ждать таймаут на каждый порт
   каждого из 254 адресов, даже если там никого нет.


3) Полная диагностика найденных устройств (имя, MAC, вендор, ОС, тип):

   netscan_x64.exe --ip 192.168.0.1-192.168.0.255 --ports 53,80,443,445,
                   161,5900-5910 --proto all --discover --info
                   --mode fast --threads 50 --batch 32
                   --out result.txt

   Добавляет для каждого найденного хоста: MAC-адрес и вендора (по базе
   OUI), грубую эвристику ОС по TTL, тип устройства по набору открытых
   портов (принтер/камера/Android/Windows и т.п.), NetBIOS имя/домен,
   mDNS-имя, LLMNR-имя компьютера, SNMP sysDescr.


4) Максимально дотошное определение имени компьютера, включая AD-домен:

   netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 445
                   --proto tcp --discover --info --deep-resolve
                   --dns-server 192.168.1.1 --mode full --threads 30

   --deep-resolve добавляет ещё два способа определения имени:
   обратный DNS (PTR) через указанный DNS-сервер (или через
   автоопределённый шлюз, если --dns-server не указан) и SMB2/NTLMSSP
   хендшейк по TCP 445 - самый надёжный источник, отдаёт NetBIOS-имя,
   NetBIOS-домен, DNS-имя компьютера и DNS-домен разом, без единой
   попытки авторизации. Работает одинаково в рабочей группе и в AD.


5) Только UDP, только DNS/NTP/SNMP - проверка сетевых служб роутера:

   netscan_x64.exe --ip 192.168.1.1 --ports 53,123,161 --proto udp
                   --mode full --threads 5 --timeout 1500

   Для этих портов сканер шлёт не пустой "пробник", а настоящие
   протокольные запросы (валидный DNS A-запрос, NTP client request,
   SNMP GetRequest community "public") - иначе большинство служб просто
   молча проигнорируют мусорный пакет и порт покажется закрытым, хотя
   служба реально работает.


6) Журнал повторяющихся сканирований одного диапазона с метками времени:

   netscan_x64.exe --ip 192.168.1.1-192.168.1.50 --ports 22,80,443
                   --proto tcp --mode full --threads 20
                   --out monitoring.txt --resume --when

   Каждый новый запуск ДОПИСЫВАЕТ результат в конец файла (не
   перезаписывает), отделяя сканирования двумя пустыми строками, и
   ставит метку времени "07:15:00  12.07.2026" перед каждым блоком.
   Удобно гонять по расписанию (планировщик задач Windows) и потом
   смотреть один растущий файл-журнал.


7) Устойчивый скан через слабый/перегруженный роутер:

   netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 80,443,445
                   --proto all --mode fast --threads 30 --batch 16
                   --retries 3 --timeout 1000

   --retries N повторяет проверку порта до N раз, если ответа не было
   (не в ущерб скорости остальных - в fast-режиме повтор идёт для
   конкретного слота, не блокируя остальные параллельные проверки).


8) Обход зарезервированных адресов диапазона отключен намеренно:

   netscan_x64.exe --ip 192.168.1.0-192.168.1.255 --ports 80
                   --proto tcp --mode full --threads 10
                   --include-reserved

   По умолчанию сканер пропускает x.x.x.0 и x.x.x.255 (это сетевой и
   широковещательный адрес обычной /24-сети, а не отдельные хосты -
   опрос broadcast-адреса даёт ложные результаты, отвечает случайный
   сосед по подсети). --include-reserved включает их обратно, если
   у вас нестандартная маска подсети и они реально нужны.


9) Оба варианта сортировки результата одновременно:

   netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 22,80,443,3389
                   --proto tcp --discover --mode fast --threads 50
                   --out result.txt --sort-by-port

   Создаёт ДВА файла: result.txt (отсортирован по IP, как обычно) и
   result_by_port.txt (та же информация, но сгруппирована по портам -
   удобно смотреть "у кого вообще открыт 3389", а не "что открыто у
   каждого хоста").


10) Обновление базы вендоров MAC-адресов перед выездом на объект без
    интернета:

    netscan_x64.exe --update-oui

    Скачивает актуальную базу OUI (IEEE, через репозиторий nmap) в
    oui.txt рядом с exe-файлом. Если файла нет вообще - вендор по MAC
    просто не будет определяться, скан при этом продолжит работать
    нормально. Файл можно скопировать вручную на изолированную машину.


ПОЛНЫЙ ФУНКЦИОНАЛ И ВОЗМОЖНОСТИ
================================================================================

--------------------------------------------------------------------------
1. АДРЕСА И ПОРТЫ
--------------------------------------------------------------------------

--ip <спец>
    Диапазон(ы) IPv4-адресов. Форматы (можно смешивать через запятую):
      - Одиночный IP:              192.168.1.5
      - Диапазон "от-до":          192.168.1.1-192.168.1.254
      - Несколько диапазонов:      192.168.1.1-192.168.1.254,10.0.0.1-10.0.0.50
    Также поддерживается перенос строки как разделитель между диапазонами.
    x.x.x.0 и x.x.x.255 внутри диапазона пропускаются автоматически (см.
    --include-reserved ниже) - это сетевой и broadcast-адрес обычной /24
    сети, а не реальные хосты.

--ports <спец>
    Список портов через запятую, с поддержкой диапазонов:
      80,443,1000-1200,500,445,53
    Дубликаты в списке автоматически схлопываются - можно не бояться
    случайно указать один порт дважды, лишний раз он не просканируется
    и не появится дважды в результате.

--proto all|tcp|udp
    Какие протоколы сканировать. При "all" TCP и UDP по умолчанию
    сканируются ОДНОВРЕМЕННО (в двух независимых наборах потоков), а не
    последовательно - это примерно вдвое быстрее. Каждый протокол
    рисует свой прогресс-бар на отдельной закреплённой строке консоли
    (работает только в настоящем окне cmd.exe, не при перенаправлении
    в файл/pipe). Принудительно вернуть последовательный порядок - см.
    --sequential.

--include-reserved
    Не пропускать x.x.x.0 и x.x.x.255 - сканировать их как обычные
    хосты. Нужно только при нестандартной маске подсети, где эти адреса
    реально являются рабочими хостами.

--------------------------------------------------------------------------
2. РЕЖИМЫ СКАНИРОВАНИЯ
--------------------------------------------------------------------------

--mode full|fast
    full - надёжный, "по одному за раз на поток" режим. Каждый поток
        обрабатывает одну проверку порта полностью (включая ожидание
        таймаута), потом берёт следующую задачу из очереди. Параллельность
        строго равна числу потоков (--threads).

    fast - настоящий асинхронный режим. Каждый поток держит открытыми
        сразу --batch соединений одновременно ("выстрелил - не жду -
        проверяю следующее - готов ответ пришёл - зафиксировал"), через
        select() узнавая, какие из них уже готовы, не дожидаясь остальных
        по очереди. Реальная параллельность = --threads x --batch.
        На несуществующих хостах (нет ARP-ответа) даёт прирост скорости
        на порядки по сравнению с full-режимом при том же числе потоков.

--threads N
    Число используемых ОС-потоков. В full-режиме - это и есть реальная
    параллельность. В fast-режиме - множитель для --batch (см. выше).
    Разумные значения: 20-100 для full, 30-100 для fast. Внутренний
    потолок - 512 потоков (у каждого ОС-потока свой стек, не стоит
    бездумно наращивать).

--batch N (по умолчанию 32, работает только в --mode fast)
    Сколько соединений один поток держит открытыми одновременно. Пример:
    50 потоков x 32 batch = 1600 одновременных проверок.

--timeout N (миллисекунды, по умолчанию 800)
    Сколько ждать ответа на один запрос перед тем как считать порт
    закрытым/недоступным.

--retries N (по умолчанию 1)
    Сколько раз повторять проверку порта, если ответа не было - полезно
    при потере пакетов на слабом/перегруженном маршрутизаторе. Работает
    и в full, и в fast режиме (в fast - повтор идёт для конкретного
    "слота", не блокируя остальные параллельные проверки).

--sequential
    Принудительно сканировать TCP и UDP по очереди вместо одновременно
    (актуально только при --proto all).

--------------------------------------------------------------------------
3. ПРОТОКОЛ-СПЕЦИФИЧНЫЕ UDP-ПРОБНИКИ
--------------------------------------------------------------------------

UDP - протокол без хендшейка: пустой "пробник" многие службы просто
молча игнорируют, если не могут распознать его как валидный запрос
(классический пример - DNS: TCP:53 находится от одного факта хендшейка,
а UDP:53 с пустым пакетом - нет, хотя служба работает). Поэтому для
следующих портов сканер отправляет НАСТОЯЩИЕ протокольные запросы вместо
пустого байта:

  - 53  (DNS)  - валидный A-запрос домена example.com
  - 123 (NTP)  - стандартный клиентский запрос (client mode 3)
  - 161 (SNMP) - GetRequest (SNMPv1, community "public") на sysDescr.0

Для всех остальных UDP-портов используется обычный минимальный пробник.

--------------------------------------------------------------------------
4. РАЗВЕДКА ЖИВЫХ ХОСТОВ: --discover
--------------------------------------------------------------------------

--discover
    Перед сканированием портов сначала быстро проверяет, какие хосты в
    диапазоне вообще существуют - ДВУМЯ независимыми способами разом:

      1. ICMP-пинг (через штатный Windows API IcmpSendEcho, БЕЗ прав
         администратора и без raw-сокетов).
      2. ARP-запрос (SendARP) - для хостов в ВАШЕЙ ЖЕ локальной подсети.
         ARP работает на канальном уровне и не обходится настройками
         "ICMP выключен на этом устройстве" - если пинг молчит, а
         устройство физически в сети, ARP всё равно его найдёт.

    Хост считается живым, если ответил хотя бы один из двух способов.
    Порты сканируются только по хостам, прошедшим эту проверку - для
    больших диапазонов (например /24) это ускоряет скан на порядки,
    потому что не тратится время на полный таймаут по каждому порту
    для каждого из сотен несуществующих адресов.

    ВАЖНО: --discover полностью исключает из результата любой хост,
    который не ответил НИ на пинг, НИ на ARP - даже если у него открыт
    порт. Для устройств с жёстко настроенным файрволом, который режет
    и ICMP тоже, это может дать "слепую зону". Для параноидальной
    перепроверки прогоните диапазон ещё раз без --discover.

--ping-timeout N (миллисекунды, по умолчанию 500)
    Таймаут именно для фазы разведки (--discover), отдельно от --timeout
    для самого скана портов.

--------------------------------------------------------------------------
5. ДИАГНОСТИКА УСТРОЙСТВ: --info
--------------------------------------------------------------------------

--info
    После скана портов собирает дополнительную информацию по каждому
    "интересному" хосту - ОДИН РАЗ НА ХОСТ, не на порт, поэтому не
    замедляет сам скан портов. Список хостов для диагностики:
      - если использовался --discover - все хосты, ответившие на
        пинг/ARP;
      - если --discover не использовался - только хосты, на которых
        реально нашёлся хотя бы один открытый TCP/UDP порт.

    Источники информации (все - широковещательные/протокольные запросы,
    не требуют паролей и прав администратора):

    MAC-адрес и вендор
        Через SendARP (для хостов в вашей локальной подсети - для
        адресов за её пределами MAC намеренно не показывается, чтобы
        не выдавать MAC пограничного маршрутизатора за реальный ответ
        удалённого хоста). Вендор определяется по базе OUI (см. ниже,
        --update-oui) - если базы нет рядом с exe, показывается только
        сам MAC без расшифровки вендора.

    TTL и грубая эвристика ОС
        TTL берётся из ICMP-ответа (бесплатно, если уже использовался
        --discover). Округление до ближайшего стандартного стартового
        значения: TTL<=64 - Linux/Android/embedded, TTL<=128 - Windows,
        TTL<=255 - сетевое оборудование/иное. Точность условная (TTL
        можно подделать вручную), но как быстрый ориентир - рабочий
        метод.

    Тип устройства по набору открытых портов
        Чистый offline-анализ уже собранных результатов, без
        дополнительных сетевых запросов: 515/631/9100 -> принтер,
        554 -> IP-камера/медиа, 5555 -> Android (ADB), 62078 ->
        iOS-устройство, 3389 -> Windows (RDP), 445+139 -> Windows/Samba,
        1900/8008/8009 -> медиа-устройство (UPnP/Cast), 22 без 445 ->
        Linux/сетевое устройство.

    NetBIOS (NBSTAT, UDP 137)
        Один запрос "*" отдаёт NetBIOS-имя компьютера и рабочую
        группу/домен.

    mDNS (UDP 5353)
        Запрос списка сервисов ("_services._dns-sd._udp.local"). Без
        полного разбора DNS-сжатия - вытаскивается самая длинная
        печатаемая ASCII-подстрока из ответа (обычно это и есть имя
        хоста или тип сервиса). Лучше всего работает для Android,
        принтеров, умных устройств, Linux.

    LLMNR (UDP 5355) - имя компьютера Windows
        Современная замена NetBIOS, которую Windows держит включённой
        по умолчанию даже когда "NetBIOS over TCP/IP" отключён вручную.
        Запрашивается PTR-запись обратного адреса, респондер отвечает
        собственным именем компьютера. Пакет отправляется с IP TTL=255
        (это обязательное по RFC 4795 требование - респондер молча
        отбрасывает запросы с иным TTL).

    SNMP sysDescr
        Если порт 161 входит в список сканируемых портов - переиспользует
        уже отправленный туда запрос и парсит текстовое описание
        устройства из ответа (например "Linux hostname 5.10.0 ...").

    Самоопрос (сканирование своего же IP)
        На практике подтверждено: Windows по какой-то причине не отвечает
        на NetBIOS/LLMNR/mDNS/SNMP-запросы, адресованные его собственному
        РЕАЛЬНОМУ IP (тот же запрос с другого устройства сети получает
        нормальный ответ). Сканер автоматически определяет свои
        собственные IP-адреса и в этом случае уходит через 127.0.0.1
        вместо реального адреса - там такой проблемы нет. Содержимое
        LLMNR-запроса при этом всё равно честно спрашивает про настоящий
        IP (не про loopback) - разделены адрес назначения пакета и адрес
        внутри самого протокольного запроса.

--sort-os
    Сортировать блок "Информация об устройствах" по эвристике ОС (TTL)
    вместо IP - удобно посмотреть все Windows-машины разом, потом все
    Linux/embedded и т.д.

--------------------------------------------------------------------------
6. УГЛУБЛЁННОЕ ОПРЕДЕЛЕНИЕ ИМЕНИ: --deep-resolve
--------------------------------------------------------------------------

--deep-resolve
    Включает --info автоматически и добавляет ещё два, самых надёжных
    способа определения имени компьютера:

    Обратный DNS (PTR)
        Запрос PTR-записи через обычный DNS-сервер - по умолчанию
        автоопределённый сетевой шлюз (можно переопределить, см.
        --dns-server). Многие DHCP-серверы регистрируют hostname
        клиента при выдаче аренды, поэтому PTR часто отдаёт настоящее
        имя компьютера даже когда NetBIOS/LLMNR по каким-то причинам
        молчат. Честно проверяется ANCOUNT (число реальных ответов) -
        если DNS-сервер вернул NXDOMAIN с SOA-записью в Authority-
        секции (это служебная запись о зоне, не ответ), она не будет
        ошибочно принята за имя хоста.

    SMB2 NEGOTIATE + NTLMSSP CHALLENGE (TCP 445)
        Самый надёжный источник имени из всех. SMB2-хендшейк БЕЗ единой
        попытки авторизации: сервер обязан прислать NTLMSSP CHALLENGE
        как часть протокола NTLM, ещё до всякой проверки логина/пароля.
        Из CHALLENGE извлекаются четыре поля разом: NetBIOS-имя,
        NetBIOS-домен/рабочая группа, DNS-имя компьютера и DNS-домен.
        Работает ОДИНАКОВО что в обычной рабочей группе, что в AD-
        домене - именно так это делают nmap/CrackMapExec/enum4linux
        для разведки. Для самоопроса используется настоящий IP (не
        loopback) - на TCP-портах такой проблемы, в отличие от UDP-
        протоколов выше, не наблюдалось.

--dns-server IP
    Свой DNS-сервер для PTR-запросов при --deep-resolve, вместо
    автоопределённого шлюза. Полезно, если в сети есть отдельный DNS-
    сервер/AD-контроллер, который ведёт более полную и точную зону,
    чем домашний роутер.

--------------------------------------------------------------------------
7. ВЫВОД И СОХРАНЕНИЕ РЕЗУЛЬТАТА
--------------------------------------------------------------------------

--out <путь>
    Файл результата (по умолчанию scan_result.txt). Формат:

        Хостов: N   Портов: N   Потоков: N   Режим: ...   Таймаут: ... мс
        Диапазон: <как введено>
        Порты: <как введено>
        Файл результатов: <путь>
        [прогресс-бар(ы)]
        Сканирование завершено за N.N сек.

        TCP
        ip:port
        ip:port
        UDP
        ip:port

        Информация об устройствах:      (только если --info)
        ip
          MAC: ... (Вендор)
          TTL: N -> ОС
          Тип (по портам): ...
          NetBIOS: имя=... группа/домен=...
          SNMP sysDescr: ...
          mDNS: ...
          LLMNR (имя компьютера): ...
          PTR (обратный DNS): ...          (только если --deep-resolve)
          SMB NetBIOS: имя=... домен=...   (только если --deep-resolve)
          SMB DNS: имя=... домен=...       (только если --deep-resolve)
        ******************************************************************
        ip
          ...

--resume, -r
    Дописывать результат в конец файла вместо перезаписи, отделяя
    разные по времени сканирования двумя пустыми строками. Удобно для
    накопительного журнала мониторинга одного и того же диапазона.

--when, -w
    Записывать дату и время сканирования перед блоком результатов, в
    формате "07:15:00  12.07.2026". Особенно полезно вместе с --resume.

--sort-by-port
    Дополнительно создаёт файл <имя>_by_port.<расширение> с теми же
    результатами, но отсортированными сначала по порту, потом по IP.
    Основной файл (сортировка по IP) при этом не меняется - оба
    варианта сохраняются одновременно.

--------------------------------------------------------------------------
8. БАЗА MAC-ВЕНДОРОВ (OUI)
--------------------------------------------------------------------------

--update-oui
    Скачивает актуальную базу соответствий MAC-префикс -> вендор с
    GitHub (репозиторий nmap, данные из официального реестра IEEE,
    ~52000 записей) в файл oui.txt рядом с exe, и завершает работу
    (не требует --ip/--ports). Скачивание идёт по HTTPS через штатный
    WinINet - работает без установки дополнительных библиотек.

    Если базы нет - определение вендора по MAC просто не работает,
    сам MAC-адрес при этом всё равно показывается. Для изолированной
    (без интернета) машины файл oui.txt можно скопировать вручную -
    сканер сам найдёт его рядом со своим exe при следующем запуске.

--------------------------------------------------------------------------
9. ПРОЧЕЕ
--------------------------------------------------------------------------

--help, -h
    Показать краткую справку по параметрам.

Индикатор запуска: первая строка "NetScan запущен, обрабатываю
параметры..." печатается сразу же при старте, ещё до разбора остальных
аргументов - чтобы не создавалось впечатление, что программа зависла в
момент запуска (актуально, если Windows Defender/SmartScreen делает
проверку репутации неподписанного exe перед первым запуском - это
происходит на стороне ОС, до начала выполнения кода сканера, и никак не
лечится на уровне самой программы, кроме подписи exe сертификатом).

Вывод в консоль работает через нативный Win32 API (WriteConsoleW) вместо
обычного printf - это надёжно отображает кириллицу на любой версии
Windows Vista-11 независимо от текущей кодовой страницы cmd.exe. При
перенаправлении вывода в файл/pipe используется обычный UTF-8.


ТРЕБОВАНИЯ И СОВМЕСТИМОСТЬ
================================================================================

  - Windows Vista, 7, 8, 8.1, 10, 11 (x86 и x64 отдельными сборками).
  - Права администратора НЕ требуются для базового сканирования и для
    всей диагностики --info/--deep-resolve.
  - Никаких сторонних драйверов (Npcap/WinPcap) не требуется и не
    устанавливается.
  - Статическая линковка - дополнительные .dll на целевой машине не
    нужны.
  - SYN-скан (как в masscan) технически невозможен без Npcap/WinPcap -
    начиная с Windows XP SP2 система блокирует произвольную отправку
    сырых TCP-заголовков через raw socket на уровне ядра. Поэтому
    --mode fast - это async connect() с высокой конкурентностью, а не
    буквальный SYN-флуд.
