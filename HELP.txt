================================================================================
                  NetScan - a console local network scanner
                            for Windows Vista - 11
================================================================================


WHAT THIS IS
================================================================================

NetScan is a lightweight console TCP/UDP local network scanner for Windows,
written in C and built with the mingw-w64 cross-compiler (compiled on Linux,
statically linked - no extra DLLs are needed on the target machine). Ships
as separate x86 (32-bit) and x64 (64-bit) builds, and runs on anything from
Windows Vista through Windows 11.

It was built as a replacement for nmap for everyday sysadmin tasks, for
situations where you want a fast, lightweight tool with a real progress
bar that not only finds open ports but, where possible, immediately
answers "what kind of device is this and what's it called" - without
installing Npcap/WinPcap and without administrator rights.

Core principles:
  - No third-party drivers (Npcap/WinPcap) - works out of the box.
  - No administrator rights required for basic scanning.
  - An honest, real-time progress bar and stats.
  - A genuinely asynchronous "fast" mode (hundreds/thousands of concurrent
    checks per thread), not an illusion created by spawning many OS threads.
  - The cost of extra diagnostics (MAC / device name / OS) is charged PER
    HOST, not per port - it doesn't slow down the port scan itself.


SYNTAX
================================================================================

netscan_x64.exe --ip <range> --ports <list> --proto all|tcp|udp
                 --threads <N> --mode full|fast [extra options]

Required: --ip, --ports
Everything else has sensible defaults.


USAGE EXAMPLES
================================================================================

1) Simplest scan of a single host on a couple of ports (full, reliable mode):

   netscan_x64.exe --ip 192.168.1.1 --ports 22,80,443 --proto tcp
                   --threads 20 --mode full

   Slow, but maximally reliable - one request per port at a time per thread.


2) Fast scan of an entire home subnet on common ports:

   netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 21,22,23,25,53,
                   80,110,143,443,445,3389,5900-5910 --proto all
                   --mode fast --threads 50 --batch 32 --discover

   --discover dramatically speeds up scans of large ranges: a fast
   ICMP+ARP sweep first finds which hosts are ACTUALLY alive, and only
   those get their ports scanned - instead of waiting out a full timeout
   on every port of every one of 254 addresses, even the ones with
   nothing listening.


3) Full diagnostics on every device found (name, MAC, vendor, OS, type):

   netscan_x64.exe --ip 192.168.0.1-192.168.0.255 --ports 53,80,443,445,
                   161,5900-5910 --proto all --discover --info
                   --mode fast --threads 50 --batch 32
                   --out result.txt

   Adds, for every host found: MAC address and vendor (from an OUI
   database), a rough OS guess from TTL, device type inferred from the
   set of open ports (printer/camera/Android/Windows/etc.), NetBIOS
   name/domain, mDNS name, LLMNR computer name, SNMP sysDescr.


4) Maximally thorough hostname resolution, including the AD domain:

   netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 445
                   --proto tcp --discover --info --deep-resolve
                   --dns-server 192.168.1.1 --mode full --threads 30

   --deep-resolve adds two more ways to resolve a hostname: reverse DNS
   (PTR) through the given DNS server (or an auto-detected gateway if
   --dns-server is omitted), and an SMB2/NTLMSSP handshake over TCP 445 -
   the most reliable source of all, returning the NetBIOS name, NetBIOS
   domain, DNS computer name and DNS domain all at once, without a
   single authentication attempt. Works the same way in a workgroup and
   in an AD domain.


5) UDP only, DNS/NTP/SNMP only - checking a router's network services:

   netscan_x64.exe --ip 192.168.1.1 --ports 53,123,161 --proto udp
                   --mode full --threads 5 --timeout 1500

   For these ports the scanner sends real protocol requests instead of
   an empty "probe" (a valid DNS A-record query, an NTP client request,
   an SNMP GetRequest with community "public") - otherwise most services
   would simply, silently ignore a garbage packet and the port would
   look closed even though the service is actually running.


6) A log of repeated scans of the same range, with timestamps:

   netscan_x64.exe --ip 192.168.1.1-192.168.1.50 --ports 22,80,443
                   --proto tcp --mode full --threads 20
                   --out monitoring.txt --resume --when

   Every run APPENDS to the end of the file (instead of overwriting it),
   separating scans with two blank lines, and stamps a timestamp
   "07:15:00  12.07.2026" before each block. Handy for running on a
   schedule (Windows Task Scheduler) and reviewing one growing log file
   afterwards.


7) A resilient scan through a weak/overloaded router:

   netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 80,443,445
                   --proto all --mode fast --threads 30 --batch 16
                   --retries 3 --timeout 1000

   --retries N retries a port check up to N times if there was no
   response (without slowing down the other checks - in fast mode a
   retry only re-arms that one slot, without blocking the other parallel
   checks).


8) Reserved addresses in the range are intentionally skipped by default:

   netscan_x64.exe --ip 192.168.1.0-192.168.1.255 --ports 80
                   --proto tcp --mode full --threads 10
                   --include-reserved

   By default the scanner skips x.x.x.0 and x.x.x.255 (the network and
   broadcast address of a normal /24 network, not individual hosts -
   probing a broadcast address gives misleading results, since some
   random neighbor on the subnet ends up answering for it).
   --include-reserved turns them back on, for the rare case of a
   non-standard subnet mask where they really are usable hosts.


9) Both sort orders for the results, at the same time:

   netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 22,80,443,3389
                   --proto tcp --discover --mode fast --threads 50
                   --out result.txt --sort-by-port

   Produces TWO files: result.txt (sorted by IP, as usual) and
   result_by_port.txt (the same data, but grouped by port - handy for
   answering "who has 3389 open" rather than "what's open on this host").


10) Updating the MAC vendor database before heading to a site with no
    internet access:

    netscan_x64.exe --update-oui

    Downloads a current OUI database (IEEE data, via the nmap
    repository) into oui.txt next to the exe. If the file is missing,
    vendor lookup by MAC simply won't happen and the scan will otherwise
    work normally. The file can be copied by hand onto an isolated
    machine.


11) Hardware/OS inventory on a network you actually administer:

    netscan_x64.exe --ip 192.168.1.1-192.168.1.254 --ports 135,445
                    --proto tcp --discover --wmi
                    --wmi-user admin --wmi-password ****
                    --wmi-domain CORP --mode full --threads 30

    Unlike everything else in this tool, --wmi requires real rights on
    the target machines (domain admin, or any account with WMI access).
    Returns exact OS version/build, last boot time, CPU core count, RAM
    size, and the currently logged-on user - the inventory you'd need to
    plan hardware upgrades or track down who's logged in where. Omit
    --wmi-user/--wmi-password entirely to use your current session (SSO)
    instead of explicit credentials.


FULL FEATURE REFERENCE
================================================================================

--------------------------------------------------------------------------
1. ADDRESSES AND PORTS
--------------------------------------------------------------------------

--ip <spec>
    One or more IPv4 ranges. Formats (can be mixed, comma-separated):
      - A single IP:                192.168.1.5
      - A "from-to" range:          192.168.1.1-192.168.1.254
      - Multiple ranges:            192.168.1.1-192.168.1.254,10.0.0.1-10.0.0.50
    A newline is also accepted as a separator between ranges.
    x.x.x.0 and x.x.x.255 inside a range are skipped automatically (see
    --include-reserved below) - these are the network and broadcast
    address of a normal /24 network, not real hosts.

--ports <spec>
    A comma-separated port list, with range support:
      80,443,1000-1200,500,445,53
    Duplicates in the list are automatically collapsed - no need to
    worry about accidentally listing a port twice, it won't be scanned
    twice and won't show up twice in the results.

--proto all|tcp|udp
    Which protocols to scan. With "all", TCP and UDP are scanned AT THE
    SAME TIME by default (in two independent sets of threads), not
    sequentially - roughly twice as fast. Each protocol draws its own
    progress bar on its own fixed console line (only works in a real
    cmd.exe window, not when output is redirected to a file/pipe). To
    force the old sequential order, see --sequential.

--include-reserved
    Do not skip x.x.x.0 and x.x.x.255 - scan them like ordinary hosts.
    Only needed with a non-standard subnet mask where these addresses
    are genuinely working hosts.

--------------------------------------------------------------------------
2. SCAN MODES
--------------------------------------------------------------------------

--mode full|fast
    full - the reliable "one at a time per thread" mode. Each thread
        handles one port check fully (including waiting out the
        timeout), then takes the next task off the queue. Concurrency
        is exactly the thread count (--threads).

    fast - a genuinely asynchronous mode. Each thread keeps --batch
        connections open at once ("fire - don't wait - check the next
        one - a reply came in - record it"), using select() to find out
        which ones are ready without waiting for the rest in turn.
        Real concurrency = --threads x --batch. On non-existent hosts
        (no ARP reply) this gives an order-of-magnitude speedup compared
        to full mode with the same thread count.

--threads N
    Number of OS threads used. In full mode this is the actual
    concurrency. In fast mode it's a multiplier for --batch (see
    above). Sensible values: 20-100 for full, 30-100 for fast. Internal
    cap: 512 threads (each OS thread has its own stack, no point in
    scaling this blindly).

--batch N (default 32, only applies to --mode fast)
    How many connections a single thread keeps open at once. Example:
    50 threads x 32 batch = 1600 concurrent checks.

--timeout N (milliseconds, default 800)
    How long to wait for a reply to a single request before considering
    the port closed/unreachable.

--retries N (default 1)
    How many times to retry a port check if there was no reply - useful
    against packet loss on a weak/overloaded router. Works in both full
    and fast mode (in fast mode, a retry only re-arms that one "slot",
    without blocking the other parallel checks).

--sequential
    Force TCP and UDP to be scanned one after another instead of at the
    same time (only relevant with --proto all).

--------------------------------------------------------------------------
3. PROTOCOL-SPECIFIC UDP PROBES
--------------------------------------------------------------------------

UDP is connectionless - many services simply, silently ignore an empty
"probe" if they can't recognize it as a valid request (the classic
example is DNS: TCP:53 gets found from the mere fact of a TCP handshake,
while UDP:53 with an empty packet doesn't, even though the service is
running). So for the following ports the scanner sends REAL protocol
requests instead of a single empty byte:

  - 53  (DNS)  - a valid A-record query for example.com
  - 123 (NTP)  - a standard client request (client mode 3)
  - 161 (SNMP) - a GetRequest (SNMPv1, community "public") for sysDescr.0

All other UDP ports use the regular minimal probe.

--------------------------------------------------------------------------
4. LIVE-HOST DISCOVERY: --discover
--------------------------------------------------------------------------

--discover
    Before scanning ports, quickly checks which hosts in the range
    actually exist - using TWO independent methods at once:

      1. ICMP ping (via the standard Windows API IcmpSendEcho, WITHOUT
         administrator rights and without raw sockets).
      2. ARP request (SendARP) - for hosts on YOUR OWN local subnet.
         ARP operates at the link layer and isn't affected by "ICMP is
         disabled on this device" settings - if ping stays silent but
         the device is physically on the network, ARP will still find it.

    A host is considered alive if either method gets a response. Ports
    are then only scanned on hosts that passed this check - for large
    ranges (e.g. a /24) this speeds things up by orders of magnitude,
    because time isn't wasted waiting out a full timeout on every port
    of every one of hundreds of non-existent addresses.

    IMPORTANT: --discover completely excludes from the results any host
    that answered NEITHER ping NOR ARP - even if it has an open port.
    For a device with a firewall configured to also block ICMP, this
    can create a blind spot. For a paranoid re-check, run the range
    again without --discover.

--ping-timeout N (milliseconds, default 500)
    Timeout used specifically for the discovery phase (--discover),
    separate from --timeout used for the port scan itself.

--------------------------------------------------------------------------
5. DEVICE DIAGNOSTICS: --info
--------------------------------------------------------------------------

--info
    After the port scan, gathers additional information for every
    "interesting" host - ONCE PER HOST, not per port, so it doesn't slow
    down the port scan itself. The host list used for diagnostics:
      - if --discover was used - every host that answered ping/ARP;
      - if --discover was not used - only hosts where at least one open
        TCP/UDP port was actually found.

    Information sources (all broadcast/protocol-level requests, none of
    them require a password or administrator rights):

    MAC address and vendor
        Via SendARP (for hosts on your local subnet - for addresses
        outside it, the MAC is deliberately not shown, so as not to pass
        off the border router's MAC as a real answer from the remote
        host). The vendor is looked up in an OUI database (see
        --update-oui below) - if the database isn't present, only the
        raw MAC is shown without a vendor name.

    TTL and a rough OS guess
        TTL comes from the ICMP reply (free if --discover was already
        used). Rounded to the nearest standard starting value:
        TTL<=64 - Linux/Android/embedded, TTL<=128 - Windows,
        TTL<=255 - network equipment/other. The accuracy is only
        approximate (TTL can be spoofed manually), but as a quick
        pointer it works well.

    Device type from the set of open ports
        A pure offline analysis of already-collected results, with no
        extra network requests: 515/631/9100 -> printer, 554 -> IP
        camera/media, 5555 -> Android (ADB), 62078 -> iOS device,
        3389 -> Windows (RDP), 445+139 -> Windows/Samba,
        1900/8008/8009 -> media device (UPnP/Cast), 22 without 445 ->
        Linux/network device.

    NetBIOS (NBSTAT, UDP 137)
        A single "*" query returns the computer's NetBIOS name and its
        workgroup/domain.

    mDNS (UDP 5353)
        A service-list query ("_services._dns-sd._udp.local"). Without
        a full DNS-compression parser - the longest printable ASCII
        substring is extracted from the reply (usually the hostname or
        service type). Works best for Android, printers, smart devices,
        and Linux.

    LLMNR (UDP 5355) - Windows computer name
        A modern replacement for NetBIOS that Windows keeps enabled by
        default even when "NetBIOS over TCP/IP" has been manually
        disabled. A reverse-address PTR record is requested; the
        responder replies with its own computer name. The packet is
        sent with IP TTL=255 (mandatory per RFC 4795 - a responder must
        silently discard requests with any other TTL).

    SNMP sysDescr
        If port 161 is in the scanned port list, reuses the request
        already sent there and parses the device's text description out
        of the reply (e.g. "Linux hostname 5.10.0 ...").

    Self-scanning (scanning your own IP)
        Confirmed in practice: for some reason Windows does not respond
        to NetBIOS/LLMNR/mDNS/SNMP requests addressed to its own REAL IP
        (the same request from another device on the network gets a
        normal reply). The scanner automatically detects its own IP
        addresses and in that case routes the request through
        127.0.0.1 instead of the real address - loopback doesn't have
        this problem. The content of the LLMNR request still honestly
        asks about the real IP (not about loopback) - the destination
        address of the packet and the address inside the protocol
        request body are handled separately.

--sort-os
    Sort the "Device information" block by the OS guess (TTL) instead of
    by IP - handy for viewing all the Windows machines together, then
    all the Linux/embedded ones, etc.

--------------------------------------------------------------------------
6. DEEPER HOSTNAME RESOLUTION: --deep-resolve
--------------------------------------------------------------------------

--deep-resolve
    Turns on --info automatically and adds two more, very reliable ways
    to resolve a computer's name:

    Reverse DNS (PTR)
        A PTR-record query via a regular DNS server - by default the
        auto-detected network gateway (can be overridden, see
        --dns-server). Many DHCP servers register the client's hostname
        when handing out a lease, so PTR often returns the real computer
        name even when NetBIOS/LLMNR are silent for some reason. ANCOUNT
        (the actual number of answers) is honestly checked - if the DNS
        server returned NXDOMAIN with an SOA record in the Authority
        section (a zone-metadata record, not an answer), it will not be
        mistaken for a hostname.

    SMB2 NEGOTIATE + NTLMSSP CHALLENGE (TCP 445)
        The single most reliable name source. An SMB2 handshake WITHOUT
        a single authentication attempt: the server must send back an
        NTLMSSP CHALLENGE as part of the NTLM protocol, before any
        login/password check even happens. Four fields are extracted
        from the CHALLENGE at once: NetBIOS name, NetBIOS
        domain/workgroup, DNS computer name, and DNS domain. Works
        IDENTICALLY in a plain workgroup and in an AD domain - this is
        exactly how nmap/CrackMapExec/enum4linux do their
        reconnaissance. For self-scanning, the real IP is used (not
        loopback) - on TCP ports, unlike the UDP protocols above, this
        problem was not observed.

--dns-server IP
    Your own DNS server for PTR queries with --deep-resolve, instead of
    the auto-detected gateway. Useful if the network has a dedicated DNS
    server/AD controller that maintains a fuller and more accurate zone
    than a home router.

--------------------------------------------------------------------------
7. WMI DIAGNOSTICS (VIA DCOM): --wmi
--------------------------------------------------------------------------

IMPORTANT: unlike everything described above (--info, --deep-resolve),
this is NOT anonymous protocol-level probing. WMI genuinely requires
rights on the target machine - either the current user's own session
(SSO) or explicit credentials. Expect it to fail on most machines you
don't administer.

--wmi
    Turns on --info automatically. Connects to \\<ip>\root\cimv2 over
    classic DCOM (CoCreateInstance + IWbemLocator::ConnectServer) and
    queries:
      - Win32_OperatingSystem: exact OS caption/version/build number
        (distinguishes Windows XP through 11, Server 2003 through 2025 -
        whatever the target actually reports), and the last boot
        date/time.
      - Win32_ComputerSystem: logical CPU core count, total RAM, and the
        currently interactively logged-on user (UserName - empty if
        nobody is logged on locally).
      - Win32_LogonSession (LogonType=2): an approximate logon time for
        the current interactive session. WQL has no ORDER BY, so on a
        machine with more than one interactive session (e.g. an RDP
        session alongside the console) this picks whichever session the
        provider happens to enumerate first, not necessarily the most
        recent - treat it as a quick pointer, not an authoritative
        answer, same spirit as the TTL-based OS guess elsewhere in this
        tool. Logoff time is NOT available the same way: WMI only
        exposes currently-active sessions, so there's nothing to query
        once a session has ended - a real logoff time would need to be
        mined from the Security event log (Win32_NTLogEvent, event ID
        4634/4647), which requires the Security log to be remotely
        readable and its auditing enabled - not implemented yet.

    Before attempting the (potentially slow) DCOM connection, the
    scanner first does its own quick TCP check against port 135 (the
    DCOM endpoint mapper) with a short, configurable-style timeout.
    ConnectServer itself has no simple timeout knob - it relies on the
    OS's default RPC/TCP timeout, which can run into the tens of
    seconds against an unreachable or filtered host. Without this
    pre-check, running --wmi across a whole range where most hosts
    don't expose DCOM would be nearly unusable.

    On failure, the specific reason is recorded and shown (e.g. "port
    135 (DCOM) unavailable", or a raw ConnectServer HRESULT such as
    0x80041015, which usually means access denied / firewalled / DCOM
    disabled on the target) - this is deliberate: with a
    rights-dependent feature like this, silent failure would be far
    more confusing than an honest error message.

--wmi-user U
    Username for WMI authentication. If omitted, the current user's
    session is used (SSO) - this only works if you're already running
    as a domain/local account with rights on the target and DCOM is
    reachable.

--wmi-password P
    Password for --wmi-user.

--wmi-domain D
    Domain for --wmi-user (optional; combined as DOMAIN\user).

--wmi-gpu
    Also queries Win32_VideoController (Name) - the GPU model. Kept
    behind its own flag since it's a "nice to have" for design-team
    hardware planning rather than a core diagnostic, and it's one more
    WMI round-trip per host.

--------------------------------------------------------------------------
8. OUTPUT AND SAVING RESULTS
--------------------------------------------------------------------------

--out <path>
    The results file (default: scan_result.txt). Format:

        Hosts: N   Ports: N   Threads: N   Mode: ...   Timeout: ... ms
        Range: <as entered>
        Ports: <as entered>
        Results file: <path>
        [progress bar(s)]
        Scan finished in N.N sec.

        TCP
        ip:port
        ip:port
        UDP
        ip:port

        Device information:                (only with --info)
        ip
          MAC: ... (Vendor)
          TTL: N -> OS
          Type (by ports): ...
          NetBIOS: name=... group/domain=...
          SNMP sysDescr: ...
          mDNS: ...
          LLMNR (computer name): ...
          PTR (reverse DNS): ...           (only with --deep-resolve)
          SMB NetBIOS: name=... domain=... (only with --deep-resolve)
          SMB DNS: name=... domain=...     (only with --deep-resolve)
        ******************************************************************
        ip
          ...

--resume, -r
    Append the results to the end of the file instead of overwriting it,
    separating scans taken at different times with two blank lines.
    Handy for a cumulative monitoring log of the same range over time.

--when, -w
    Write the date and time of the scan before the results block, in
    the format "07:15:00  12.07.2026". Especially useful together with
    --resume.

--sort-by-port
    Additionally creates a file <name>_by_port.<ext> with the same
    results, sorted first by port, then by IP. The main file (sorted by
    IP) is left unchanged - both variants are saved at the same time.

--------------------------------------------------------------------------
9. MAC VENDOR DATABASE (OUI)
--------------------------------------------------------------------------

--update-oui
    Downloads a current MAC-prefix -> vendor mapping from GitHub (the
    nmap repository, sourced from the official IEEE registry, ~52,000
    entries) into oui.txt next to the exe, then exits (does not require
    --ip/--ports). Downloaded over HTTPS via the standard WinINet API -
    no extra libraries need to be installed.

    Without the database, vendor lookup by MAC simply doesn't happen -
    the MAC address itself is still shown either way. For an isolated
    (offline) machine, oui.txt can be copied over by hand - the scanner
    will find it next to its own exe on the next run.

--------------------------------------------------------------------------
10. MISCELLANEOUS
--------------------------------------------------------------------------

--help, -h
    Show a short summary of the available options.

Startup indicator: the line "NetScan started, parsing arguments..." is
printed immediately at startup, before any other argument parsing - so
the program doesn't appear to hang right after launch (relevant if
Windows Defender/SmartScreen is doing a reputation check on an unsigned
exe before its first run - that happens at the OS level, before the
scanner's own code even starts running, and can't be fixed from inside
the program itself, short of signing the exe with a certificate).

Console output goes through the native Win32 API (WriteConsoleW) instead
of plain printf - this reliably displays Cyrillic (and other non-ASCII
text) on any Windows Vista-11 version regardless of the current cmd.exe
code page. When output is redirected to a file/pipe, plain UTF-8 is used
instead.


REQUIREMENTS AND COMPATIBILITY
================================================================================

  - Windows Vista, 7, 8, 8.1, 10, 11 (separate x86 and x64 builds).
  - Administrator rights are NOT required for basic scanning or for any
    of the --info/--deep-resolve diagnostics.
  - No third-party drivers (Npcap/WinPcap) are required or installed.
  - Statically linked - no extra .dll files are needed on the target
    machine.
  - A SYN scan (like masscan's) is technically impossible without
    Npcap/WinPcap - since Windows XP SP2 the OS has blocked arbitrary
    raw TCP header injection at the kernel level. That's why --mode fast
    is a high-concurrency async connect() scan, not a literal SYN flood.

        CPU core count, RAM size, currently logged-on user, optional GPU
        model. Supports both SSO (current session) and explicit
        --wmi-user/--wmi-password/--wmi-domain credentials. DONE.

  [ ] The same diagnostics via WinRM as an alternative transport to DCOM
        - needed for environments where WinRM is enabled but classic
        DCOM (port 135 + a dynamic RPC range) is blocked or disabled.
        INVESTIGATED AND DEFERRED: mingw-w64's wsman.h only declares the
        session-management calls (WSManInitialize/WSManCreateSession/

        *writing* a WinRM plugin - it's missing every client-side
        invoke/shell/get function (WSManCreateShell, WSManRunShellCommand,
        WSManGetObject, etc.), and there's no import library for
        wsmsvc.dll in the toolchain either. Hand-declaring those
        functions and their structs from memory, with no real Windows
        machine available to verify the ABI, was judged too risky (a
        wrong struct layout wouldn't just fail to link - it could
        misbehave against a real target). The realistic path forward is
        a raw WS-Management SOAP-over-HTTP client built on WinINet
        (already used for --update-oui), talking to port 5985/5986
        directly and relying on WinINet's built-in NTLM/Negotiate
        handling for auth - more work than the native API would have
        been, but it doesn't depend on any header/library completeness.
        Deferred in favor of other TODO items for now.

  [x] Approximate interactive logon time via WMI (Win32_LogonSession).
        DONE, with the caveat above about multiple sessions.

  [ ] Logoff time - needs Security event log mining (Win32_NTLogEvent,
        event ID 4634/4647) rather than a simple WMI class query; not
        yet implemented.

  [ ] Idle time - CORRECTION: an earlier version of this TODO claimed
        this was fundamentally impossible to get remotely. That was
        wrong, and conflated two different APIs. GetLastInputInfo() is
        indeed local-only - but that's not what quser/qwinsta actually
        use. They're built on the Terminal Services API (wtsapi32.dll):
        WTSOpenServer(hostname) + WTSQuerySessionInformation(...,
        WTSSessionInfo, ...) returns a WTSINFO struct with LastInputTime,
        LogonTime, ConnectTime, and DisconnectTime all in one call - and
        it works remotely, exactly like quser /server:hostname does.
        Both the header and the import library (libwtsapi32.a) are
        present in the mingw-w64 toolchain, unlike the WinRM situation
        above - no ABI-guessing risk here. This turns both the logon-time
        TODO item above and the deferred logoff-time item into something
        answerable via a single, well-supported API, likely replacing
        the WMI Win32_LogonSession approach entirely. Not yet
        implemented, but no longer blocked - next in line.

  [ ] Task Scheduler (ITaskService, COM/DCOM, taskschd.h) as a general
        "run something once on the target and collect the result"
        channel - both header and import library (libtaskschd.a) are
